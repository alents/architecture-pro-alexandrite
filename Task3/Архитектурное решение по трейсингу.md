### 1. Системы, которые следует покрыть трейсингом

**Онлайн-магазин -> Shop API -> Shop DB / 3D-хранилище**

- Загрузка 3D-моделей
- Создание заказа
- Валидация и сохранение заказа

**CRM API -> RabbitMQ -> MES API**

- Отправка сообщений о новых заказах и их статусах

**MES API -> MES DB / 3D-хранилище / RabbitMQ**

- Расчёт стоимости изделия (длительная операция: 2–30 минут)
- Сохранение результата расчёта
- Обновление статусов заказа

**CRM -> CRM API -> Shop DB / 3D-хранилище / RabbitMQ**

- Получение и отображение информации о заказах
- Создание/обновление заказов через API

**Потенциальные узкие места и точки зависания:**

- Долгий расчёт стоимости в MES (особенно для сложных моделей)
- Очередь RabbitMQ (задержки или потеря сообщений)
- Запросы к БД при фильтрации и пагинации (дашборд операторов)
- Синхронизация статусов между MES и CRM

### 2. Данные, которые должны попадать в трейсинг

**Общие для всех сервисов:**
- Уникальный ID заказа
- Время поступления запроса
- Источник запроса (онлайн-магазин, CRM, API-партнёр)
- Статус обработки на каждом шаге
- Время начала и окончания каждого шага
- Время выполнения запросов в БД
- Ошибки

**Онлайн-магазин / Shop API:**
- Продолжительность загрузки 3D-модели
- Размер и количество полигонов модели
- Результат валидации заказа

**MES API:**
- Время начала и окончания расчёта стоимости
- Продолжительность операций с файловым хранилищем
- Ошибки расчёта

**CRM API:**
- Время обработки запроса для отображении списка заказов
- Ошибки при синхронизации статусов

**RabbitMQ:**

- Состояние очереди (задержка сообщений в очереди, количество сообщений)

### 3. Мотивация

Внедрение трейсинга в систему «Александрит» необходимо для того, чтобы контролировать полный жизненный цикл заказа, выявлять узкие места и оперативно реагировать на ошибки. Сейчас компания сталкивается с проблемами задержек и потерянных заказов, что негативно влияет на удовлетворённость клиентов и доход. Трейсинг позволит видеть путь каждого запроса к системе по работе с заказами через все сервисы — онлайн-магазин, CRM, MES и точно определять, где и почему произошла задержка или ошибка.

**Преимущества для компании:**

- Снижение количества просроченных заказов и жалоб клиентов
- Возможность оперативного реагирования на сбои и узкие места
- Улучшение планирования ресурсов и нагрузки на систему

**Возможные метрики, на которые повлияет внедрение трейсинга:**

**Технические:**

1. Среднее время расчёта стоимости заказа в MES
2. Время доставки сообщений через RabbitMQ
3. Время отклика CRM API и онлайн-магазина при создании и обновлении заказов
4. Время отклика MES API на запросы поиска заказов и назначения заказа оператору

**Бизнес-метрики:**

1. Процент заказов, выполненных в срок
2. Количество жалоб клиентов на задержку заказа
3. Среднее время от создания заказа до его готовности к производству



### 4. Предлагаемое решение

**Технологии и компоненты:**

- **OpenTelemetry SDK** — интеграция на уровне сервисов (Shop API, CRM API, MES API) для сбора trace/span.
- **Tempo (Grafana)** — хранение и индексация трассировок для последующего анализа..
- **Grafana Dashboard** —  визуализация трассировок, анализ времени выполнения операций, выявление узких мест и ошибок в обработке заказов..
- **Java/.Net агенты** (zero-code инструментация)  —  "перехватывает" популярные библиотеки и фреймворки и автоматически добавляет spans для HTTP/DB/MQ/JVM/.NET без изменений кода.
- **OpenTelemetry Collector** — централизованный агент для приема, обоаботки и экспорта телеметрии из сервисов в **Tempo**

**Что будет сделано:**

1. Добавлены span-атрибуты для заказа, например, `order_id` и другие необходимые бизнес-параметры.
2. Трейсинг охватит ключевые точки:
- Создание/обновление заказа в Shop API и CRM API
- Загрузка 3d-моделей
- Работа с заказами в MES (просмотр, назначение операторам)
- Расчёт стоимости и обновление статусов заказов в MES и CRM
3. Добавлены новые связи от сервисов к **OTEL Collector** для отправки трассировок.

**Результат:**

- Видимость всего пути запроса по сервисам системы
- Быстрое выявление узких мест и ошибок
- Возможность отслеживания SLI по времени обработки запросов

### 5. Компромиссы

**Трассировать всё слишком дорого.**
Если собирать трассировки со всех операций в продакшене, хранилище быстро заполнится, а расходы сильно вырастут. Поэтому придётся использовать сэмплирование — фиксировать только часть запросов и все ошибки. При этом мы теряем полные данные по всем операциям, но сохраняем возможность выявлять узкие места и критические сбои.

**Не все системы можно покрыть трейсингом.**
Некоторые внешние или проприетарные компоненты (например, закрытые модули MES или сторонние сервисы) не всегда позволяют добавить нужные данные. В этих местах останутся «слепые зоны».

**Не все части системы можно подключить «из коробки».**
OpenTelemetry-агенты поддерживают большинство современных фреймворков, но если в системе используются собственные библиотеки, самописные решения или легаси-код, передачу контекста придётся внедрять вручную. Это повышает стоимость и увеличивает сроки внедрения.

**Потребуется поддержка и обслуживание.**
Коллектор, агенты, схемы данных — всё это нужно обновлять и контролировать. Это добавляет постоянную нагрузку на команду.

### 6. Аспекты безопасности

1. **Контролируемый доступ:** доступ к трейсингу (Grafana, Tempo) будет выдаваться только сотрудникам с корпоративным SSO и ролями, которым действительно нужна телеметрия — *Developer, Support, QA, DevOps*.

2. **Защита данных:** будет включено шифрование трафика (HTTPS/TLS) и производиться фильтрация чувствительных данных  (ФИО, телефон, e-mail, адрес, пароль и т.п.)) — в телеметрию должны попадать только технические атрибуты.
3. **Изоляция и аудит:** инфраструктура трейсинга будет работать во внутренней корпоративной мети сети, а все действия пользователей будут логироваться.

### 7. Предлагаемое решение

После внедрения трейсинга система сможет автоматически отслеживать выполнение операций над заказами, учитывая оба потока:

1. **Внутренние заказы** — создаются пользователями в онлайн-магазине и проходят через CRM.
2. **Заказы партнёров** — поступают через MES API и создаются в CRM после получения сообщения из очереди.

Каждая операция фиксируется как span в составе trace со следующими данными:

- `trace_id` — уникальный идентификатор цепочки выполнения запроса (trace), генерируется OTEL SDK
- `duration` — время выполнения операции, (`end_time` - `start_time`), вычисляется автоматически  
- `status.code` — статус выполнения (OK/ERROR), генерируется SDK
- `service.name` — сервис, где спан был создан
- Дополнительные атрибуты (http.method, db.query, custom бизнес-данные, например, `order_id`) — автоматически или разработчиком

Сбор трассировок осуществляется через **OpenTelemetry Collector**, который получает трейсы (spans) с фронтендов и бэкендов по OTLP, отправляет их в **Tempo** для хранения и генерирует на их основе метрики (latency, error rate, RPS и др.) через `traces→metrics pipeline`, доступные для **Prometheus**. Хотя **OpenTelemetry SDK** позволяет собирать метрики напрямую в сервисах, это избыточно при уже внедрённом мониторинге через Micrometer, JMX-метрики и Prometheus scrape — трасcировки дополняют существующие метрики, обеспечивая полный контекст через exemplars.

**Prometheus** собирает метрики (scrape) из **OTEL Collector**, а **Grafana** используется  для построения дашбордов и настройки алертов. Если длительность спана превышает порог или возникает ошибка, уведомление отправляется через настроенные **Notification Channels** (Telegram, Email и т.д.).

**Tempo** тинтегрируется с **Prometheus/Grafana**: у метрик в **Prometheus** можно включить *exemplars*, которые ссылаются на конкретный `trace_id` в Tempo. Это позволяет при срабатывании алерта быстро перейти от метрики к полному контексту трассировки конкретного запроса.

Данное решение позволяет выявлять узкие места и ошибки в обработке заказов, контролировать производительность сервисов, сокращать задержки и быстро получать полный контекст операции через `trace_id`.
