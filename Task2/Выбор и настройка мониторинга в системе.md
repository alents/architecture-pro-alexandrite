### Мотивация

Внедрение мониторинга решит следующие проблемы:

1. Позволит следить за состоянием системы в целом и ее отдельных частей, своевременно получать сигналы об ошибках и быстрее принимать меры к их исправлению. Например, пользователи интернет-магазина начали получать ошибку 500 при попытке создания заказа. Разработчику или специалисту эксплуатации сразу придет alert с информацией об ошибке и ее источнике. Это позволит оперативно отреагировать на проблему сразу после ее возникновения, не дожидаясь жалоб и обращений от клиентов.

2. Позволит выявлять проблемы на раннем этапе, не дожидаясь сбоя системы. Например, мониторинг позволяет отслеживать использование ресурсов (cpu, оперативная память, диск) и своевременно уведомлять о превышении пороговых значений. Это даст возможность запланировать выделение дополнительных ресурсов либо работы по оптимизации.
3. Позволит быстро находить узкие места в системе. Например, мониторинг сигнализирует превышении максимального размера очереди задач на расчет стоимости изделий. Разработчик смотрит в дашбоард сервиса MES API и видит, что сервис перегружен запросами API (высокий RPS). Либо наоборот в сервисе имеется бутылочное горлышко, не дающее оптимально утилизировать ресурсы.
4. Позволит повысить удовлетворенность пользователей, так как проблемы будут решаться своевременно.  



### Выбор подхода к мониторингу

1. Для мониторинга расчета стоимости заказов  будем использовать метод USE. Утилизация - смотрим процент использования CPU, насыщенность - смотрим количество задач на расчет стоимости от CRM в очереди RabbitMQ, ошибки - смотрим количество ошибок при расчетах 

2. Для мониторинга работы Интернет-магазина, CRM, MES API будем использовать метод RED, так как важно контролировать нагрузку, процент ошибок и время выполнения запросов

3. Для мониторинга файлового хранилища будем использовать метод USE. U - IOPS, % CPU/MEM, % full; S - latency, queue length; E - storage health

4. Для мониторинга баз данных будем использовать USE для ресурсов серверов (диски, CPU, память) и RED для  запросов от приложений (QPS, Duration, Connection Errors)

### Отслеживаемые метрики

1. Number of `dead-letter-exchange` letters in RabbitMQ. Нужна для отслеживания ошибок обработки задач расчета стоимости заказов или превышения TTL. Ярлыки: queue - имя исходной очереди, reason - причина попадания в DLX (unack/ttl), vhost - хост (release/prod) 
2. Number of message `in flight` in RabbitMQ. Нужна для отслеживания производительности модуля расчета стоимости заказов в (сервисе MES API). Высокие значения метрики означают, что модуль не справляется и  очередь задач растет. Ярлыки: Ярлыки: queue - имя очереди, vhost - хост (test/release/prod)
3. Number of requests (RPS) for internet shop API. Показывает общую картину нагрузки на бэкенд интернет-магазина. Помогает планировать масштабирование, диагностировать узкие места. Например, при маленьком RPS выскокий процент использования CPU - указывает необходимость оптимизации сервиса. Ярлыки: app - имя сервиса, profile (test/release/prod)
4. Number of requests (RPS) for MES API. Показывает общую картину нагрузки на MES API. Помогает планировать масштабирование, диагностировать узкие места. Например, если тормозит поиск заказов в MES, то причина может быть в нагрузке на API со стороны внешних пользователей. Данная метрика это покажет. Ярлыки: app - имя сервиса, profile (test/release/prod)
5. CPU % for MES API, CPU % for CRM API, CPU % for for MES API. Метрика утилизации CPU является очень важной для любого сервиса. Рекомендуется анализировать вместе с метрикой RPS.  Ярлыки: app - имя сервиса, profile (test/release/prod)
6. Memory Utilisation for shop API, Memory Utilisation for CRM API, Memory Utilisation for MES API. Метрика использования памяти наряду с метрикой утилизации CPU является обязательной метрикой. Помогает выявлять утечки памяти либо необходимость дополнительного выделения памяти. Ярлыки: app - имя сервиса, area(heap/nonheap), profile (test/release/prod)
7. Memory Utilisation for shop db instance, Memory Utilisation for MES db instance. Метрика нужна как для определения необходимости масштабирования сервера СУБД (не хватает памяти), так и для  выявления проблем: ошибки в конфигурации, неэффективные запросы, отсутствие индексов, высокая конкуренция и т.д. Ярлыки: instance - имя инстанса БД.
8. Number of active connections for shop db instance, Number of active connections for MES db instance. Высокие значения данной метрики часто указывают на проблему с замедлением выполнения запросов (возможно слетел план выполнения, либо не создали индекс). Ярлыки: instance - имя инстанса БД.
9. Number of idle connections for shop db instance, Number of idle connections for MES db instance. Высокие значения данной метрики указывают либо на неправильную настройку пулов соединений, либо на утечку соединений. Ярлыки: instance - имя инстанса БД
10. Response time (latency) for shop API, Response time (latency) for CRM API, Response time (latency) for MES API. Данная метрика позволяет своевременно выявить проблему с падением производительности сервиса. Ярлыки: app - имя сервиса, profile (test/release/prod)
11. Free Size of S3 storage, Free Size of shop db instance, Free Size of MES db instance. Метрика необходима, чтобы отслеживать остаток свободного места и своевременно позаботиться о его увеличении либо об удалении неиспользуемых данных. Ярлыки: instance - имя инстанса.
12. Size of S3 storage, Size of shop db instance, Size of MES db instance. Метрика позволяет отслеживать скорость роста базы данных/хранилища, делать прогнозы, планировать бюджет на выделение дополнительных ресурсов. Ярлыки: instance - имя инстанса.
13. Response status for shop API, Response status for  CRM API, Response status for MES API. Метрика является одним из главных индикаторов корректной работы сервиса. Если число ошибочных статусов (5xxx) растет, то это сигнализирует о наличии сбоя.  Ярлыки: app - имя сервиса, status_code(200,500,503), profile (test/release/prod)
