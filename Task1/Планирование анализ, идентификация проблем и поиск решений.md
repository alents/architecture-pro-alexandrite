## 1. Существующие и потенциальные проблемные места

1. Монолитная архитектура MES приводит к следующим проблемам:

   - Взаимное влияние отдельных функций приложения друг на друга:  вычисление стоимости изделий, регистрация заказов  и управление жизненным циклом заказов, обработка запросов API и сообщений из очередей. Особенно сильное влияние оказывает функционал вычисления стотимости, так как он наиболее ресурсоёмкий 
   - Невозможно горизонтальное масштабирование отдельных функций
   - Вертикальное масштабирование не даст ощутимого эффекта, так как тяжелый функционал расчета стоимости будет утилизировать все доступные ресурсы и оказывать негативное влияние на отзывчивость API.

2. Внутреннее API MES выставлено наружу и делится между внутренними и внешними пользователями системы, что создает следующие риски:

   - Увеличение нагрузки со стороны внешних пользователей оказывает прямое влияние на работоспособность MES, повышает вероятность отказов сервиса, что может привести к простою производства изделий и прямым финансовым потерям 

   -  Нет возможности ограничить количество входящих запросов от внешних пользователей в случае перегрузки сервиса или DDoS-атаки и одновременно сохранить возможность работы внутренним пользователям
   - Усложнение доработок API, невозможность изменения контрактов API без доработок на стороне внешних пользователей. Требуется более тщаетельное тестирование внешних интеграций при любой доработке. 
   - Усложнение API для внешних пользователей, которым, скорее всего, нужна только небольшая часть его функциональности
   - Нет возможности использовать различные настройки безопасности для внутренних пользователей и внешних интеграций, например сделать разные способы аутентификации.

3. Инстансы сервисов развернуты на виртуалках (EC2). Это сильно замедляет масштабирование и делает его более дорогим, снижает устойчивость системы к сбоям. 

4. Отсутствие пайплайнов CI/CD для релиза и прода замедляет вывод новых релизов, увеличивает количество ошибок при обновлении сервиса (человеческий фактор).

5. Отсутствует автоматизация тестирования, что приводит к увеличению трудозатрат на ручное тестирование и к большему количеству ошибок, попавших в прод.

## 2. Инициативы в порядке приоритета

1. Выделяем из сервиса MES API тяжелый функционал расчета стоимости изделий в отдельный новый сервис. Задачи сервису будут ставиться асинхронно через брокер RabbitMQ из сервиса MES API.
3. Разворачиваем новый сервис в кластере Kubernetes, настраиваем HPA/autoscaling, CI/CD
3. Изолируем внешние интеграции с помощью API Gateway, настраиваем аутентификацию,  rate limiting/circuit braker.  
4. Разворачиваем мониторинг в кластере и добавляем сбор метрик в новый сервис. В первую очередь настраиваем метрики утилизации CPU, памяти, количества ошибок, количества запросов в секунду и времени выполнения запроса.
5. Покрываем автотестами самые важные сервисы:  сервиса расчета стоимости и MES API.  
6. Внедряем централизованное логирование (EFK или Grafana Loki)
7. Переносим в Kubernetes остальные сервисы, кроме баз данных, s3-storage и брокера RabbitMQ, настраиваем CI/CD.
8. Внедряем кэширование
9. Настраиваем tracing (внедряем OpenTelemetry и Jaeger)
10. Покрываем остальные сервисы автотестами
11. Настраиваем нагрузочное тестирование
12. Создаем группу эксплуатации. Зона ответственности: установка релизов, настройка мониторинга (дашборды, алерты), слежение за состоянием системы, заведение инцидентов в баг-трекер команды разработки (2-я линия поддержки).
13. Создаем группу 1-й линии поддержки. Зона ответственности: прием обращений клиентов, первичный анализ инцидентов и передача на 2-ю линию при необходимости.
14. Нанимаем еще одного инженера по тестированию (один инженер не справится с текущим тестированием и работой над автоматизацией тестирования одновременно)
15. Выделяем сервис-адаптер для внешних интеграций. Это позволит развивать внутренний API, не оказывая влияния на внешних пользователей. 
16. Делаем новую версию внешнего API, убрав из нее неиспользуемые внешними пользователями функции и упростив payload.

Указанный порядок инициатив вызван тем, что первоочередная задача - это снять боль бизнеса и стабилизировать работу системы в максимально сжатые сроки с минимальными трудозатратами. Цель дальнейших изменений - это обеспечить устойчивость системы к увеличению нагрузки (масштабирование), повысить наблюдаемость, упростить поддержку и увеличить скорость и качество новых релизов. 

Основную нагрузку на систему создаёт модуль расчёта стоимости изделий. Проблема в том, что он выполняется внутри того же сервиса, который отвечает за работу с заказами и обработку API-запросов (как внутренних, так и внешних пользователей). Профили нагрузки у этих частей системы существенно отличаются. Расчёт стоимости — это длительная CPU-интенсивная операция, выполняемая асинхронно. Работа с заказами, напротив, носит в основном синхронный характер и предполагает обработку большого числа запросов, каждый из которых сам по себе потребляет мало CPU, но требует минимального времени отклика. Из-за сочетания этих разных типов нагрузки время ответа сервиса увеличивается: CPU постоянно занят расчётом стоимости, что снижает доступные ресурсы для обработки пользовательских запросов.

Следующая по значимости проблема - это совместное использование API MES как внутренними так и внешними пользователями. Сейчас нет возможности ограничивать трафик от внешних пользователей в случае проблем с перегрузкой системы.

Далее идет проблема с отсутствием наблюдаемости в системе. О проблемах менеджеры узнают от клиентов, а не от системы мониторинга.

Поэтому первой задачей будет вынести модуль расчета стоимости изделий в отдельный сервис. Причем для экономии времени новый сервис будет копией сервиса MES API, в котором будет использоваться только функционал расчета стоимости. Взаимодействие между сервисами будет осуществляться через RabbitMQ, что потребует минимального объёма работ. Рефакторинг нового сервиса будет запланирован на следующий этап после решения проблемы с производительностью системы. 

Затем необходимо развернуть новый сервис в Kubernetes. Это позволит быстро развертывать сервис, гибко настраивать масштабирование, причем делать это динамически в зависимости от нагрузки. Развертывание остальных сервисов в Kubernetes - менее приритетная большая задача, которую можно запланировать на следующий этап (после решения проблемы с производительностью).

Далее необходимо разделить внутренних и внешних пользователей, направив запросы последних к MES API через API Gateway, где можно настроить ограничение входящих запросов в зависисмости от текущей нагрузки на сервис. 

Затем необходимо решить задачу настройки мониторинга: развертывание Prometheus, настройка метрик в сервисах и т.д.

Остальные задачи делаем на следующем этапе (часть задач можно делать параллельно с задачами первого этапа, если есть свободные ресурсы)



## 3. Целевая архитектура через 6 месяцев

Через полгода я вижу такую целевую архитектуру:

- Модуль расчёта стоимости изделий вынесен из сервиса в MES API в отдельный микросервис (containerized).
- Внешние пользователи работают через API-Gateway (rate limiting).
- Взаимодействие MES API сервиса расчета стоимости через RabbitMQ.
- Сервис  расчета стоимости запущен в Kubernetes как деплоймент с HPA, с отдельным node pool для CPU-heavy задач.
- CI/CD настроен,  автотесты покрывают критичные сценарии.
- Мониторинг (Prometheus + Grafana), трейсинг (Jaeger), централизованное логирование  (EFK или Garafana Loki).



## 4. Если можно сделать только 3 пункта за полгода — что выбрать и почему

1. Вынести модуль расчёта стоимости изделий в отдельный сервис + настроить взаимодействие через RabbitMQ.
   Это решает основную проблему (влияние ресурсоемких операций на API (работа с заказами)) и даст немедленный ффект для бизнеса. Без этого остальные улучшения мало что изменят.

2. Развернуть и настроить API Gateway для запросов к внутреннему API MES для внешних пользователей.
   Это позволит ограничить внешних пользователей при превышении порога нагрузки на систему и даст возможность нормально работать с ней операторам.

3. Внедрить мониторинг и логирование  + настроить алерты.
    Сделать систему наблюдаемой, быстрее выявлять проблемы и выяснять причины инцидентов. Мониторинг позволит так же своевременно масштабировать систему либо ограничивать запросы от внешних пользователей.
